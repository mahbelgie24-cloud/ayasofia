## ٢. سلطة الموافقة (Approval Authority)

### مطلوب موافقة Human:

- إطلاق أي إصدار للإنتاج
- تغيير في نطاق المشروع (scope change)
- أي ميزة تمس المال أو العملاء مباشرة
- شراء خدمات/تراخيص مدفوعة
- تعطيل/حذف بيانات حقيقية
- تغييرات كبرى في واجهة المستخدم

### مطلوب موافقة Sonnet:

- دمج أي كود في develop/main
- أي تغيير في db/schema.ts (هجرات)
- إضافة تبعية (dependency) جديدة
- تغيير في هيكل المجلدات
- كل قرار معماري (ADR)

### لا يحتاج موافقة (صلاحية DeepSeek):

- كيفية كتابة الكود داخل مهمة محددة
- تسمية المتغيرات والدوال (ضمن المعايير)
- ترتيب كتابة الاختبارات
- الهيكل الداخلي للملف الواحد

## ٣. بوابات الجودة (Quality Gates)

### Gate 1: Self-Check (DeepSeek)

```
قبل التقديم للمراجعة:
✅ tsc --noEmit — 0 errors
✅ npm run lint — 0 errors
✅ npm run test — all pass
✅ لا parseFloat على أسعار
✅ لا تجاوز لـ requireStaffSession
```

### Gate 2: Code Review (Sonnet)

```
قبل الدمج:
✅ 13 بُعد مراجعة (انظر REVIEW_SYSTEM.md)
✅ كل الدرجات ≥ 3
✅ لا مخاطر حرجة
✅ الاختبارات الذاتية للمراجع ناجحة
```

### Gate 3: Human Approval

```
قبل الإطلاق:
✅ الميزة تعمل كما هو متوقع
✅ اختبار Human (UAT) ناجح
✅ لا شكاوى من الفريق
```

### تجاوز البوابات

- **لا يمكن تجاوز Gate 1 و Gate 2 أبدًا**
- يمكن تجاوز Gate 3 للميزات غير المرئية (backend-only, bug fixes) بموافقة Human خطية

## ٤. قواعد التصعيد (Escalation Rules)

### متى يُصعّد DeepSeek → Sonnet:

1. غموض في المواصفة لا يمكن حله
2. اكتشاف تعارض مع كود موجود
3. اكتشاف خطر أمني أو خطأ في التصميم
4. المهمة أكبر من التقدير الأصلي بأكثر من ٢×
5. صعوبة تقنية تتطلب إعادة تصميم

**لا تصعّد:** أخطاء نحوية، تحسينات طفيفة، تفضيلات شخصية.

### متى يُصعّد Sonnet → Human:

1. تغيير Scope غير متوقع
2. اكتشاف خطر أمني/تجاري كبير
3. حاجة لقرار بشري (مفاضلة بين خيارين)
4. مهمة فشلت في ٣ دورات مراجعة
5. اقتراب موعد الإطلاق ومهمة حرجة متأخرة
6. نفاد موارد (تجاوز free tier limits)

**لا تصعّد:** أسئلة تقنية بحتة، تأخيرات طفيفة، مشاكل تم حلها بالفعل.

## ٥. سياسة الإصدارات (Versioning Policy)

```
الإصدار: v<MAJOR>.<MINOR>.<PATCH>

الحالي: v0.1.0 (مرحلة ما قبل الإطلاق)

MAJOR = 0: تطوير ما قبل الإنتاج
  MINOR: مرحلة جديدة (Phase)
  PATCH: إصلاحات وتحسينات

بعد الإطلاق:
  MAJOR: تغييرات غير متوافقة مع السابق
  MINOR: ميزات جديدة متوافقة
  PATCH: إصلاحات أخطاء
```

## ٦. تعريف الجاهزية (Definition of Ready)

المهمة جاهزة للتنفيذ عندما:

- [ ] المواصفة (Feature Spec) مكتوبة ومراجعة
- [ ] المهمة مقسمة إلى Task Cards واضحة
- [ ] كل Task Card تحتوي: وصفًا، ملفات محددة، معايير قبول، خطة اختبار
- [ ] لا أسئلة مفتوحة بدون إجابة
- [ ] التبعيات (dependencies) محددة ومتوفرة
- [ ] تقدير الجهد واقعي (≤ جلسة واحدة)

---

## ٧. تعريف الإنجاز (Definition of Done)

كل مهمة تعتبر منجزة عندما:

- [ ] كل معايير القبول (AC) محققة
- [ ] `tsc --noEmit` يمر
- [ ] `npm run lint` يمر (0 أخطاء)
- [ ] `npm run test` يمر
- [ ] مراجعة الكود (Sonnet) ناجحة
- [ ] لا تحذيرات ESLint غير مبررة
- [ ] الكود مدمج في develop
- [ ] الوثائق محدثة (CHANGELOG, CURRENT_STATE)
- [ ] لا دَيْن تقني غير موثق

كل مرحلة تعتبر منجزة عندما:

- [ ] تعريف الإنجاز الخاص بالمرحلة (spec §13) محقق
- [ ] كل المهام مكتملة
- [ ] Human مؤكد الرضا

## ٩. سياسة الكود الموروث (Legacy Code Policy)

- **لا تحذف كودًا** لمجرد أنه "قديم" — إلا إذا كان غير مستخدم فعليًا
- **لا تعيد كتابة كود يعمل** — إلا إذا كان يعيق مهمة حالية
- **إذا لمسته، اختبره** — أي ملف يُعدل يجب أن تُشغل اختباراته
- **إذا كسرته، أصلحه** — لا تترك كودًا مكسورًا خلفك
