## ١. مبدأ المراجعة

> **لا كود يُدمج بدون مراجعة. لا استثناءات.**

المراجعة ليست "تدقيقًا شكليًا". إنها بوابة الجودة الوحيدة قبل أن يلمس الكود بيانات حقيقية. المراجع (Sonnet) مسؤول مسؤولية كاملة عن جودة ما يمر من خلاله.

---

## ٢. أبعاد المراجعة (Review Dimensions)

كل مراجعة تُقيم ١٣ بعدًا:

### ٢.١ المعمارية (Architecture)

- هل التغيير يتبع النمط المعماري (Modular Monolith)؟
- هل الملفات في الطبقة الصحيحة (UI / Application / Data)؟
- هل يوجد تسريب بين الطبقات (UI يتحدث إلى DB مباشرة)؟
- هل القرار يتماشى مع ADRs السابقة؟

### ٢.٢ جودة الكود (Code Quality)

- هل الكود يتبع CODING_STANDARDS.md؟
- هل التسميات واضحة ووصفية؟
- هل الدوال قصيرة ومركزة (< 50 سطرًا)؟
- هل الملفات معقولة الحجم (< 300 سطر)؟
- هل يوجد تكرار غير ضروري (DRY)؟
- هل التعقيد مبرر (KISS)؟

### ٢.٣ القراءة (Readability)

- هل كود الجلسة الواحدة مفهوم بدون الرجوع للمواصفة؟
- هل التعليقات تشرح "لماذا" وليس "ماذا"؟
- هل الأنواع (TypeScript types) واضحة وتشرح نفسها؟

### ٢.٤ القابلية للصيانة (Maintainability)

- هل التغيير معزول (تغيير في ملف واحد لا يكسر ١٠ ملفات)؟
- هل يمكن لمطور جديد فهم التغيير في < 5 دقائق؟
- هل الواجهات (interfaces) مستقرة؟

### ٢.٥ القابلية للتوسع (Scalability)

- هل التصميم يسمح بإضافة حالات جديدة بدون تعديل جوهري؟
- مثال: إضافة قناة طلب جديدة = قيمة enum جديدة فقط، لا تعديل checkout-core

### ٢.٦ الأمان (Security)

- هل Server Action يبدأ بـ `requireStaffSession` (إن تطلب)؟
- هل الصلاحيات (roles) مفروضة بشكل صحيح؟
- هل المدخلات مُتحقق منها؟
- هل الأسعار مُعادة الحساب server-side؟
- هل `idempotencyKey` موجود في كل كتابة؟
- هل يوجد تسرب للمفاتيح (secrets)؟
- لا service-role client في Client Component

### ٢.٧ الأداء (Performance)

- هل الاستعلامات محسنة (لا N+1، استخدام inArray)؟
- هل المكونات Server-side حيث أمكن؟
- هل الصور محسنة (`<Image>` لا `<img>`)؟
- هل المعاملات (transactions) لا تحبس قاعدة البيانات طويلاً؟

### ٢.٨ الوصول (Accessibility)

- هل touch targets ≥ 44px?
- هل الصور لها alt text?
- هل الأخطاء مرتبطة بالحقول (aria-describedby)؟
- هل focus management سليم؟
- هل التباين اللوني كافٍ؟

### ٢.٩ الاختبارات (Testing)

- هل التغييرات المنطقية (pricing, checkout, auth) مغطاة باختبارات؟
- هل اختبارات الحالات الحدية موجودة (empty, invalid, edge cases)؟
- هل نمط AAA (Arrange-Act-Assert) متبع؟
- هل الاختبارات مستقلة وقابلة للتكرار؟

### ٢.١٠ التوثيق (Documentation)

- هل الكود الجديد موثق بـ JSDoc إن لزم؟
- هل القرارات المعمارية موثقة في ADR؟
- هل التغيير مذكور في CHANGELOG؟

### ٢.١١ تجربة المطور (Developer Experience — DX)

- هل التغيير سهل الفهم؟
- هل توجد تحذيرات ESLint غير مبررة؟
- هل TypeScript types دقيقة (لا `any`)؟

### ٢.١٢ تجربة المستخدم (User Experience — UX)

- هل الواجهة الجديدة تتبع UI_UX_GUIDELINES.md؟
- هل النصوص بالعربية؟
- هل التصميم يتبع العلامة التجارية (ألوان، خطوط، زوايا)؟
- هل رسائل الخطأ مفهومة للمستخدم النهائي؟

### ٢.١٣ الدَيْن التقني (Technical Debt)

- هل التغيير يُضيف دَيْنًا تقنيًا؟
- هل هناك "TODO" أو "FIXME" غير موثقة؟
- هل يُفضل التبسيط الآن أم لاحقًا؟

## ٣. قالب تقرير المراجعة (Review Report)

انظر `templates/reviews/REVIEW_REPORT_TEMPLATE.md` للقالب الكامل.

### ٣.١ هيكل التقرير

```
# Review Report — [Task ID] [Task Title]

## Summary
## Review Result: ✅ Approved / ⚠️ Changes Requested / ❌ Rejected

## Scores (1-5 per dimension)
## Findings
## Risks
## Required Actions
## Approval Status
```

### ٣.٢ نظام التسجيل (Scoring)

| الدرجة | المعنى                        |
| ------ | ----------------------------- |
| 5      | ممتاز — يفوق التوقعات         |
| 4      | جيد — يفي بالمتطلبات          |
| 3      | مقبول — توجد ملاحظات طفيفة    |
| 2      | ضعيف — يحتاج تعديلات          |
| 1      | غير مقبول — يحتاج إعادة كتابة |
| N/A    | لا ينطبق على هذا التغيير      |

### ٣.٣ نتائج المراجعة (Review Outcomes)

#### ✅ Approved (موافقة)

- كل الدرجات ≥ 3
- لا مخاطر حرجة أو عالية
- كل الإجراءات المطلوبة منجزة

#### ⚠️ Changes Requested (تعديلات مطلوبة)

- توجد درجة 2 في بعد واحد
- توجد مشاكل متوسطة يجب إصلاحها
- المهندس يعود إلى Implementation ← Revision

#### ❌ Rejected (مرفوض)

- توجد درجة 1 في بعد واحد أو أكثر
- توجد مخاطر حرجة
- التصميم خاطئ جوهريًا
- يُصعّد إلى Human لاتخاذ قرار

## ٤. دورة المراجعة (Review Cycle)

```
DeepSeek يُقدم ──→ Sonnet يُراجع
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      ✅ Approved    ⚠️ Changes    ❌ Rejected
          │             │             │
          ▼             ▼             ▼
      إلى Human     DeepSeek      تصعيد إلى
      للموافقة      يُعدل         Human
          │             │             │
          ▼             ▼             ▼
        اكتمال       إعادة         قرار:
                    تقديم         إعادة/إلغاء/
                                  تأجيل
```

**الحد الأقصى للتعديلات:** ٣ دورات مراجعة لنفس المهمة. بعد ٣ دورات، يُصعّد إلى Human لمناقشة ما إذا كانت المهمة تحتاج إعادة تصميم.

## ٥. قواعد المراجع (Reviewer Rules)

1. **كن صارمًا في المال والأمان.** لا تتهاون في هذين البعدين أبدًا.
2. **كن بنّاءً.** كل ملاحظة = وصف المشكلة + سبب كونها مشكلة + اقتراح حل (إن أمكن).
3. **لا تفرض ذوقك الشخصي.** إذا كان الكود يتبع المعايير لكن بأسلوب مختلف — اقبله.
4. **اشرح "لماذا".** لا تقل فقط "هذا خطأ". قل "هذا خطأ لأن...".
5. **مجمل قبل التفاصيل.** ابدأ بالأخطاء المعمارية الكبيرة قبل التعليقات النحوية الصغيرة.
6. **لا تراجع نصف كود.** إما أن تراجع المهمة كاملة أو لا تراجعها.

---

## ٦. قواعد المنفذ (Implementer Rules — DeepSeek)

1. **اقرأ المراجعة كاملة قبل التعديل.** افهم السياق.
2. **لا تأخذ الملاحظات بشكل شخصي.** الهدف كود أفضل، ليس نقدًا.
3. **اسأل عند الغموض.** إذا لم تفهم ملاحظة — اسأل في تقرير إعادة التقديم.
4. **عدّل فقط ما طُلب.** لا "تحسن" أشياء إضافية في جولة المراجعة.
5. **أعد تشغيل الاختبارات.** دائمًا.
